# PROTOTYPE · Skynet 观察台（Web 平台原型，可丢弃）

**这个原型回答的问题：** Skynet 的 Web 平台应该长什么样？leader 怎样看清员工对 Coding Agent 的使用情况与工作情况？

- 依据：[PRD v1.0](../../docs/requirements/PRD.md) §7「Web 与 MCP 的产品界面」，以及 2026-09-24 新增的报表需求和 2026-09-28 新增的员工能力评估需求（见下文“范围变更”）。
- 设计 DNA：`hallmark study https://calendly.com/`，只取结构、配色倾向与字体角色，不复制品牌资产、插图或专有字体。
- 数据全部是合成的示例数据（`data.js` + `metrics.js` 用固定种子生成，刷新结果不变），不连接真实服务。

## 运行

直接双击 `index.html`，或者在仓库根目录执行：

```bash
python -m http.server 4173 --directory prototypes/web-platform
```

然后打开 <http://localhost:4173/>。

## 本轮新增（2026-09-24）

1. **数据报表**：谁用了多少 Token、会话里产出了什么，以及每个会话的产效比、提示词分析、响应与等待。
2. **自动去重、拾取、组装会话**：处理网络重试与重复投递、续聊复制的历史、压缩代次、子会话、离线补传。无法确定谱系时保持分离并提示确认。
3. **对话视图**：会话以对话框形式展示，工具调用默认隐藏；两条消息之间标出等待时长，超过 10 分钟会高亮。
4. **活动记录**：按时间节点记录每次对话，可以按人、Agent、项目、事件类型筛选，点击后跳到原句。

## 本轮新增（2026-09-28）：员工能力评估与员工画像

需求：告诉 leader 哪些员工用 Coding Agent 工作的能力较好、哪些较差；并提供按员工垂直切分的视图。

**评估模型**（`metrics.js` 中的 `prof()`，页面在 `proficiency.js`）：

| 维度 | 回答的问题 | 指标（0 分 → 100 分） |
| --- | --- | --- |
| 使用深度 | 是否把 Agent 用进日常工作 | 活跃天数占比 30% → 90%；活跃日会话数 0.6 → 1.8 |
| 需求表达 | 提示词是否写清楚 | 首条提示词要素覆盖 30% → 75%；Agent 追问率 20% → 3% |
| 迭代效率 | 来回修改多不多 | 返工率 28% → 5%；无返工会话占比 20% → 85%；每条已验证结果的轮次 14 → 3 |
| 验证把关 | 结果有没有经过验证 | 已验证占比 50% → 95%；运行测试的会话占比 15% → 80%（只看实现、修复、重构、测试类） |
| 产出转化 | 投入是否变成可核对的结果 | 已验证结果与产效比，都除以团队同类任务的均值或中位数：0.5× → 1.4× / 1.5× |
| 协作节奏 | Agent 是否常被卡住 | 权限等待中位数 6 分钟 → 0.8 分钟；10 分钟以上等待占比 35% → 5% |

- **综合指数**：六个维度加权平均，权重有三套方案可切换：默认 20/20/20/20/15/5、重产出、重质量。没有数据的维度不参与，权重按比例重算。
- **等级**：72 分及以上为较好，60–71 为一般，60 以下为需提升。分档按页面显示的整数判断。
- **可信度**：≥ 8 个会话且 ≥ 40 条提示词为高，≥ 5 个会话且 ≥ 25 条为中，其余为低。客户端待信任时降一级。可信度低时不评级，显示“待定”。误差按 ±26/√会话数 显示。
- **公平处理**：
  - 固定锚点，不与同事互相比较，所有人都可能同时“较好”。
  - 产出类指标按任务类型校正；测试只对需要测试的任务类型要求。
  - 单项少于 3 个样本不计分；后续追问本就简短，所以只看首条提示词。
- **示例结论**（合成数据，接入至今，默认权重）：
  - 较好：林悦 80、韩秋 78
  - 一般：陈牧 64（可信度中）、周启航 61
  - 需提升：许若溪 55
  - 待定：赵一鸣（4 个会话，且 Codex Desktop 待信任）

**员工画像页的结构**：
1. 结论：等级、指数与误差、一句话总结、强项与优先提升项、辅导建议
2. 能力维度：本人得分对照团队中位数；展开后可以看到原始值、锚点和得分
3. 使用数据：活跃天数、会话、Token、已验证结果、代码变更；三张每日小图；按 Agent 和任务类型的分布
4. 工作内容与阻塞
5. 协作方式：
   - 提示词要素，与团队水平对比
   - 代表性会话与返工较多的会话，都可以跳到原句
   - 等待回复与权限等待
6. 会话明细
7. 最近活动：可跳到活动记录
8. 趋势：W38 → W39 哑铃图
9. 复核备注：员工与 leader 都可以补充背景，备注不会改动评估数据

## 范围变更（需要确认后写入 PRD）

> **2026-09-28 的能力评估与现有文档直接冲突，原型只作界面参考，正式实现前需要先确认。** 冲突点：
> - [v2-prompt.md](../../docs/requirements/v2-prompt.md) §6 守则第 1 条（不合成总分，不做按人排名）与 AC-28
> - [PRD.md](../../docs/requirements/PRD.md) US 71、§5、Out of Scope（自动绩效评分、员工排名）
> - [CONTEXT.md](../../CONTEXT.md)「绩效参考」（首版不生成自动评分或排名）
> - [v1-scope.md](../../docs/requirements/v1-scope.md)、[discovery.md](../../docs/requirements/discovery.md) Q8
> - [v1-acceptance.md](../../docs/requirements/v1-acceptance.md) AC-13
> - [solution-design.md](../../docs/architecture/solution-design.md) 活动统计一节
>
> 这些文档尚未修改。原型为缓和冲突做了这些处理：
> - 按等级分组，组内按姓名排列，不出名次和榜单
> - 显示误差与可信度，样本不足时不评级
> - 每个分数都能展开到原始数值
> - 页面写明“不代表整体绩效，需要人工复核”
> - 提供复核备注
>
> 如果确认要做，需要改写上述条款，并补一条 ADR。

以下是 2026-09-24 那一轮的处理方式，仍然适用于报表页。

PRD v1.0 明确“不产生 AI 绩效分数或排名”，也规定 Token、消息数量、并发时长不能用来证明工时或员工价值（US 71、§5、Out of Scope）。本轮需求中的**产效比**与**响应及时性**都触及这条边界。原型的处理方式如下：

- **不合成总分，不按人排名**：报表页的人员表格固定按姓名排列，只有会话明细表允许排序。（2026-09-28 的能力评估新增了综合指数与等级分组，见上方冲突说明。）
- **比值拆开给出**：产效比的分子（已验证结果）和分母（百万 Token）都会显示；只对 Token 已知的会话计算；只在同类任务之间参考。
- **未知不计为 0**：Codex Desktop 不上报用量，相关会话单独标为“未知”。
- **等待不等于怠工**：同时标出“等待期间在其他会话中活动”。权限等待单列，它反映的是 Agent 被阻塞的流程问题。
- **证据分级**：任务类型、提示词要素、返工都标为“模型推断”；只有带工具结果佐证的结果才计入“已验证”。

建议用一条 ADR 记录这次范围调整，并同步更新 PRD 的 US 71 与 Out of Scope。

## 设计 DNA 摘要（来自 calendly.com）

- **表面**：亚麻色底 → 玉兰白面板（圆角 24px）→ 白色对象；墨色为午夜蓝，次要文字为钢灰。
- **强调色**：矢车菊蓝只用于焦点、选中与“今天”；主按钮用墨色。
- **字体角色**：Geist 用于界面，Noto Serif SC 用于分析叙述，Geist Mono 用于原件。
- **图表色**：从 DNA 的蓝、橙、青、紫取值，经 `validate_palette.js` 在浅色与深色下校验通过（相邻色对与散点全对比都通过）。
