日期：2026-09-28。产品形态：在 V1（Web + MCP server + 员工端采集器）之上扩展 Web 与 MCP 的查询、报表和评估能力；员工端不新增任何日常操作。

## Problem Statement

V1 让管理者能按日、按周阅读员工的工作主题、过程、结果与阻塞，并追溯到原文证据。管理者（leader）还想清楚掌握员工**怎样使用** Coding Agent，但现有视图回答不了这些问题：

- 谁用了多少 Token，换来了什么可核对的产出；每个会话的投入与产出之比是多少。
- 员工怎样写提示词，哪些写法导致反复返工。
- Agent 返回消息后，员工多久给出下一条指令；Agent 在哪些权限请求上被卡住。
- 某个时间段里，谁在什么时间和 Agent 进行了什么对话。
- 会话读起来像日志，工具调用淹没了对话本身。
- 平台说会话已经去重和组装，但管理者看不到它是怎样做的，也就难以信任统计数字。
- 最重要的一点：**哪些员工用 Coding Agent 工作的能力较好，哪些较差**。管理者需要知道该向谁学习、该辅导谁、辅导什么，并希望对每位员工有一个集中的视图，而不是在多个报表之间拼凑。

这些问题都很容易被误读：
- Token、消息数量和等待时长本身不代表价值或投入。
- 任务类型不同，产出天然不同。
- 样本少时结论不稳定。
- 部分字段来自模型推断，部分客户端不上报用量。

如果直接按原始数字排名，会误伤员工，也会让平台变成考勤工具。

## Solution

V2 在 V1 的原件、规范化事件和分析结果之上增加四类能力。它们全部来自同一个指标服务，Web、MCP 与导出的数值一致。

1. **看清数据从哪来**：会话组装与去重留下审计记录。新增“数据处理”页，会话详情增加“组装与去重”面板。
2. **读懂会话与时间线**：会话默认以对话视图展示，工具调用默认隐藏。新增活动记录，按北京时间逐条列出对话事件。
3. **看到使用情况**：
   - 新增四个报表页：用量与产出、会话产效、提示词分析、响应与等待。
   - 团队概览增加本周 KPI 与人员汇总，员工周视图增加使用画像。
4. **知道谁用得好、谁需要帮助**：
   - 新增**使用能力评估**，覆盖六个维度：使用深度、需求表达、迭代效率、验证把关、产出转化、协作节奏。
   - 按固定锚点给出“较好 / 一般 / 需提升 / 待定”的等级与综合指数。
   - 新增“员工一览”和按员工垂直切分的“员工画像”。

评估的定位是辅导参考，不是绩效分。为此设定以下约束：
- 固定锚点，不在同事之间比较。
- 按任务类型校正。
- 样本不足或采集不完整时不评级。
- 每个分数都能展开到原始数值和原文。
- 不出名次，不列榜单。
- 员工与管理者都能看到依据，并可追加复核备注。

所有已认证用户都能查看全部数据，沿用 ADR-0002。

### V2 产品流程

1. **看全局**：打开团队概览，查看本周 KPI、覆盖矩阵、人员汇总和每人的使用能力等级。
2. **看结论**：进入员工一览，按等级分组看谁较好、谁需要提升、谁暂时待定，以及一句理由。
3. **看个人**：进入员工画像。从结论、能力维度到使用数据、工作内容、协作方式、会话、活动与趋势，完整了解一个人。
4. **核证据**：从任何数字、示例或活动条目跳到对话视图中的原句，或时间线中的证据位置。
5. **补充与更正**：
   - 追加复核备注。
   - 更正任务类型、提示词要素或返工判定。
   - 指标与评估自动重算并保留版本。
6. **维护数据链**：在“数据处理”页查看以下内容：
   - 从拾取到报告的链路
   - 组装记录
   - 待确认谱系
   - 各 Agent 的上报覆盖率

### 范围和发布标准

| 项目 | V2 要求 |
| --- | --- |
| 数据与验收前提 | 开发复用 V1 的原件、规范化事件与分析数据链；G2（可靠存档）与 G3（真实分析链）仍须实际通过，不能用开发完成代替验收；不用假数据单独构建报表 |
| 数据来源 | 全部指标来自一个指标服务，可从原件全量重算；Web、MCP、导出一致 |
| 组装与去重 | 每个会话都有可查询的组装记录；无法确定谱系时保持分离并提示 |
| 阅读 | 对话视图、活动记录，以及证据锚点与对话锚点的跳转 |
| 报表 | 用量与产出、会话产效、提示词分析、响应与等待；团队概览与员工周视图增强 |
| 使用能力评估 | 六个维度、固定锚点、三套权重方案、等级与可信度；员工一览与员工画像；复核备注；结果版本化 |
| 守则 | 不出名次或榜单；未知不计为 0；比值同时给出分子与分母；等待不等于怠工；推断字段可更正 |
| 无障碍与适配 | 每张图有表格视图；320—1920 px 无横向滚动；浅色与深色对比度达标 |

## User Stories

编号接续 PRD v1.0 的 1—71，便于统一追踪。格式沿用“作为某类使用者，我希望某项能力，以便获得某种价值”；编号不表示必须拆成独立的开发任务。

### 会话组装与去重

72. 作为管理者，我希望同一段工作无论经过网络重试、续聊、上下文压缩还是离线补传，在报表中都只计一次，以便用量和活动数字可信。
73. 作为已认证用户，我希望看到每个会话由哪些来源文件与快照代次组装而成，以便核查存档的来龙去脉。
74. 作为已认证用户，我希望看到每个会话去除了多少重复内容及原因（网络重试或重复投递、续聊复制的历史、压缩摘要派生内容），以便确认去重没有删掉真实活动。
75. 作为已认证用户，我希望看到每个会话的谱系决策（续聊合并、子会话侧链、离线补传并入、无法确定而保持分离），以便理解会话之间的关系。
76. 作为管理者，我希望无法确定谱系的会话保持分离，并标为“待确认谱系”，以便不同工作或不同员工的记录不被默默合并。
77. 作为已认证用户，我希望在会话详情侧栏直接看到“组装与去重”面板，以便就地判断这个会话的数据是否完整。
78. 作为平台维护者，我希望“数据处理”页展示当日拾取、接收分块、去重、组装、解析与指标、报告各环节的计数，以便发现链路卡在哪一步。
79. 作为平台维护者，我希望看到原文可见延迟的 P95，以便监控是否满足 60 秒目标。
80. 作为平台维护者，我希望组装记录表可以按组装状态（已组装、组装中、存在缺口、待确认谱系）筛选，以便集中处理异常会话。
81. 作为平台维护者，我希望看到待确认谱系的列表和原因，以便跟进无法自动判定的情况。
82. 作为管理者，我希望看到各 Agent 的 Token 上报覆盖率，以便知道哪些用量属于未知。
83. 作为已认证用户，我希望“数据处理”页说明去重规则，以便理解哪些内容会被视为重复。
84. 作为已认证用户，我希望查阅统一的指标口径表，以便知道每个数字的定义、来源和可信级别。

### 对话视图

85. 作为管理者，我希望会话默认以对话框形式展示用户与 Agent 的消息，以便像读聊天记录一样快速理解会话。
86. 作为管理者，我希望工具调用默认隐藏、需要时一键展开，以便阅读时不被大量工具输出打断。
87. 作为管理者，我希望隐藏工具调用时，下一条 Agent 消息上注明“N 次工具调用（已隐藏）”，以便知道 Agent 在两条消息之间做了多少工作。
88. 作为管理者，我希望两条消息之间显示等待回复的时长，10 分钟以上的等待高亮，以便看出会话在哪里停住。
89. 作为管理者，我希望长等待旁标注“期间在其他会话中活动”，以便不把并行工作误读为停工。
90. 作为已认证用户，我希望接入前旧内容、离线补传、上下文压缩、采集缺口和进行中的会话都有明确标识，以便判断材料的时间属性与完整度。
91. 作为已认证用户，我希望消息原文只展示、不改写，Agent 自述但没有工具结果佐证的内容标“无工具结果佐证”，以便区分事实与陈述。
92. 作为已认证用户，我希望仍可切换到时间线与原件 JSONL，以便逐个事件核查。
93. 作为已认证用户，我希望报告里的证据链接跳到时间线的原位置，对话链接跳到对应消息并高亮，以便从结论直达原文。
94. 作为已认证用户，我希望子会话在对话中以链接形式出现，以便跟随并行工作的细节。
95. 作为已认证用户，我希望长会话的对话分段加载，以便大会话也能流畅阅读。
96. 作为已认证用户，我希望搜索结果包含对话原句并能直接跳到那条消息，以便按内容找到对话位置。

### 活动记录

97. 作为管理者，我希望按北京时间逐条查看对话事件，以便知道什么时间发生了什么对话。事件包括：
    - 会话开始与结束
    - 提问、Agent 回复与追问
    - 长等待与权限等待
    - 上下文压缩、采集缺口
    - 离线与补传
98. 作为管理者，我希望每条记录显示时间点、员工、会话、Agent、项目和原句摘录，截断处有省略号，以便不打开会话也能了解内容。
99. 作为管理者，我希望按日期、员工、Agent、项目和事件类型筛选活动记录，以便聚焦关心的范围。
100. 作为管理者，我希望点击活动记录就跳到对话中的原句，以便查看上下文。
101. 作为管理者，我希望在活动记录顶部看到当天的“对话节奏”泳道图，以便一眼看出全天节奏。泳道图的画法：
     - 每名员工一行
     - 会话条按 Agent 着色
     - 提问为点，返工提问为空心点
     - 长等待为浅灰段
     - 有一条“现在”线
102. 作为管理者，我希望迟到的数据按来源时间归期并标“补传”，以便活动记录不把旧活动算作今天的活动。
103. 作为管理者，我希望从员工画像的“最近活动”直接进入已带上该员工与日期筛选的活动记录，以便连续追查。

### 报表通用

104. 作为管理者，我希望所有报表页共用一行筛选（时间范围、员工、Agent、项目），并作用于整页，以便不同图表的口径一致。
105. 作为管理者，我希望每张图都能切换为等价的表格视图，以便读取精确数值，也方便无障碍访问。
106. 作为管理者，我希望页面标出数据截至时间并链接指标口径，以便知道数字的新鲜度与含义。
107. 作为管理者，我希望未上报的数值显示“未知”，合计写成“已知部分 + N 个会话未知”，以便不把缺失当成零。
108. 作为管理者，我希望比值同时展示分子与分母，并注明“只在同类任务之间参考”，以便不被单一比值误导。
109. 作为管理者，我希望模型推断的字段带有“模型推断”标注，以便正确权衡其可信度。

### 用量与产出

110. 作为管理者，我希望看到所选范围内的整体投入与产出，以便一眼把握全局，包括：
     - Token 输入与输出（已知部分，外加未上报的会话数）
     - 会话、提示词、工具调用
     - 已验证结果（附仅声称的数量）
     - 代码变更、测试通过率、会话内提交
111. 作为管理者，我希望看到每人按 Agent 堆叠的 Token，未上报的单独标“未知”，以便了解谁用了多少、用的是哪种 Agent。
112. 作为管理者，我希望看到每人产出表（会话、已验证结果、代码变更、测试、提交），每列使用独立比例尺，以便不同量纲互不挤压。
113. 作为管理者，我希望看到会话散点图（Token × 已验证结果），以便发现高投入、低产出的会话：
     - 筛选员工时高亮此人，其余作为灰色参照
     - Token 未知的会话放在单独的“未知”列
114. 作为管理者，我希望看到每人每日的 Token 小图，以便观察使用节奏。

### 会话产效

115. 作为管理者，我希望页面顶部用口径卡说明产效比、代码产出与等待占比，以便正确解读。
116. 作为管理者，我希望看到按任务类型分行的产效比分布，并标出中位数，以便只在同类任务之间比较。
117. 作为管理者，我希望看到“值得复盘的会话”，以便挑出最值得讨论的会话。入选条件为：
     - Token 高于 P75 且没有已验证结果
     - 声称多于已验证
     - 返工 ≥ 2
118. 作为管理者，我希望会话明细可以按各列排序，选中后显示“Agent 工作 / 等待回复 / 等待权限 / 缺口”的分段条，以便理解一次会话的时间花在哪里。

### 提示词分析

119. 作为管理者，我希望看到提示词数、中位长度、提供上下文的比例、返工率、无返工会话比例和 Agent 追问率，以便了解团队如何与 Agent 沟通。
120. 作为管理者，我希望看到员工 × 要素（目标、约束、上下文、验收标准）的热力表，以便找出每人的写法短板。
121. 作为管理者，我希望看到“上一条是否提供上下文”与下一轮返工率的对比，并注明相关不等于因果，以便形成可验证的改进假设。
122. 作为管理者，我希望看到按长度分段的数量与返工率，用两张图展示、不共用坐标轴，以便判断提示词长短与返工的关系。
123. 作为管理者，我希望看到任务类型构成，以便了解 Agent 被用在哪些工作上。
124. 作为员工，我希望看到正反两类写法示例，并能跳到原句，以便学习好的提示词。
125. 作为员工，我希望得到一条针对我的写法建议（标“模型推断”），以便有具体的改进方向。

### 响应与等待

126. 作为管理者，我希望页面用口径卡写明“等待不等于怠工，不用于考勤”，以便所有读者用同一口径理解。
127. 作为管理者，我希望看到等待回复的中位数与 P90、10 分钟以上的占比、权限等待中位数，以及期间在别处工作的占比，以便了解 Agent 返回后员工的响应情况。
128. 作为管理者，我希望看到星期 × 小时的等待中位数热力图，以便发现一天中响应较慢的时段。
129. 作为管理者，我希望看到每人的等待分布并标出中位数，以便了解个体差异。
130. 作为员工，我希望看到“让 Agent 停得最久的权限请求”并附允许列表建议，以便减少不必要的阻塞。

### 团队概览与员工周视图

131. 作为管理者，我希望团队概览顶部有本周 KPI 行，并附每日趋势小图，以便打开平台就掌握本周概况。
132. 作为管理者，我希望团队概览底部有“本周人员汇总”，人员固定按姓名排列，以便横向浏览而不形成排名。汇总包括：
     - 会话，Token（已知部分 + 未知会话数）
     - 已验证结果、代码变更
     - 提示词与返工率、等待中位数
     - 覆盖状态
133. 作为管理者，我希望本周人员汇总中有“使用能力”一列（等级与指数），点击可进入员工画像，以便从全局直接下钻到个人。
134. 作为管理者，我希望员工周视图有“使用画像”，并能带着员工筛选跳到报表，以便在读周报时同时看到使用情况。使用画像包括本周的：
     - Token、已验证结果
     - 提示词与返工率
     - 等待中位数
     - 每日 Token 小图

### 使用能力评估：员工一览

135. 作为管理者，我希望平台直接告诉我哪些员工用 Coding Agent 工作的能力较好、哪些一般、哪些需要提升、哪些暂时无法判断，以便决定向谁学习、辅导谁。
136. 作为管理者，我希望每个等级分组列出员工姓名、综合指数和一句理由，以便不逐个打开也能理解结论。理由的写法：
     - 较好者列强项
     - 一般和需提升者列优先提升项
     - 待定者说明原因
137. 作为管理者，我希望每位员工有一张卡片，以便快速了解其各维度情况。卡片显示：
     - 等级、综合指数、误差、可信度
     - 六个维度的得分
     - 关键数据：会话、提示词、已验证结果、返工率
138. 作为管理者，我希望切换评估范围（本周、上周、接入至今），以便区分近期表现与长期能力。
139. 作为管理者，我希望在“默认 / 重产出 / 重质量”三套权重方案之间切换，以便按团队当前的侧重查看结论。
140. 作为管理者，我希望样本不足或采集覆盖不完整的员工显示“待定”，而不是给出等级，以便不根据不充分的数据下结论。
141. 作为管理者，我希望客户端待信任等覆盖问题直接提示在卡片上，以便知道评估只基于部分数据。
142. 作为员工，我希望评估采用固定锚点、不在同事之间比较，所有人都可能同时达到“较好”，以便评估公平并鼓励经验分享。
143. 作为员工，我希望评估不出名次、不列 Top / Bottom 榜单，组内按姓名排列，以便评估用于成长而不是排名。
144. 作为已认证用户，我希望页面提供评估方法与口径说明，以便理解并质疑结论。说明涵盖：
     - 维度、指标、锚点
     - 权重、等级、可信度
     - 公平校正
     - 用途

### 员工画像（按员工垂直切分）

145. 作为管理者，我希望在一个页面看到某位员工的全部情况，以便不用在多个报表之间拼凑。页面包括：
     - 结论、能力维度
     - 使用数据、工作内容、协作方式
     - 会话、最近活动、趋势
     - 复核备注
146. 作为管理者，我希望画像顶部有目录并能跳到各节，以便在长页面中快速定位。
147. 作为管理者，我希望画像结论给出等级、综合指数、误差、可信度和一句总结，以便一眼得出判断。总结句写出强项和优先提升方向，并注明依据了多少会话和提示词。
148. 作为管理者，我希望看到针对优先提升维度的辅导建议，以便安排具体的辅导。
149. 作为管理者，我希望每个能力维度显示本人得分与团队中位数参照，并可展开看到各指标的原始数值、锚点、得分和样本数，以便核查每个分数的来源。
150. 作为管理者，我希望低于 60 分的维度默认展开，以便先看到短板的依据。
151. 作为管理者，我希望画像中的使用数据包含以下内容，以便了解使用规模与节奏：
     - 活跃天数、会话与提示词
     - 已知 Token、已验证结果
     - 代码变更与测试
     - 每日会话、每日 Token、每日已验证结果三张小图
152. 作为管理者，我希望看到此人使用的 Agent 与任务类型分布，以便理解其工作构成。
153. 作为管理者，我希望画像呈现此人的工作主题与记录到的阻塞（来自日报与周报），以便把使用能力与实际工作联系起来。
154. 作为管理者，我希望看到此人的沟通方式，以便有针对性地指导：
     - 首条提示词中各要素的出现率，与团队水平对比
     - 返工率、追问率、无返工会话比例、提示词中位长度
155. 作为管理者，我希望看到此人的代表性会话（有已验证结果且无返工）和返工较多的会话，并能跳到原句，以便用具体例子开展辅导。
156. 作为管理者，我希望看到此人的等待回复与权限等待情况、各时段的等待中位数，以及停得最久的权限请求，以便发现流程上的阻塞。
157. 作为管理者，我希望看到此人在所选范围内的会话明细（Token、提示词、已验证、产效比、返工、等待占比），以便逐个核查。
158. 作为管理者，我希望看到上周到本周综合指数与各维度的变化，并在上周没有会话时明确提示，以便判断趋势方向。
159. 作为管理者，我希望在画像中直接切换到该员工的日工作视图和周工作视图，以便在同一处阅读工作内容。
160. 作为员工，我希望能查看自己的画像与评估依据，以便了解改进方向。
161. 作为员工或管理者，我希望在画像上追加复核备注（例如“本周以方案评审为主”），备注保留作者与时间，且不改变评估数据，以便为评估补充背景。
162. 作为已认证用户，我希望更正任务类型、提示词要素或返工判定后，相关指标与评估自动重算并保留旧版本，以便推断错误能被纠正。
163. 作为已认证用户，我希望每次评估结果都记录评估模型版本、输入范围和所用分析版本，以便追溯当时的结论如何得出。
164. 作为管理者，我希望评估模型的锚点、权重或阈值调整后生成新版本，而不覆写旧结果，以便比较调整前后的变化。
165. 作为管理者，我希望员工在所选范围内没有会话时看到明确的空状态，以便不把“没有数据”误读为“能力差”。

### MCP

166. 作为已认证用户，我希望通过 MCP 查询报表摘要，数值与 Web 在同一范围下一致，以便在 Agent 中直接使用平台数据。
167. 作为已认证用户，我希望通过 MCP 分页查询活动记录，以便在 Agent 中回顾某个时间段的对话。
168. 作为已认证用户，我希望通过 MCP 分页读取会话对话，并可选择是否包含工具调用，以便在 Agent 中阅读会话。
169. 作为已认证用户，我希望通过 MCP 查询指标口径，以便 Agent 正确解释数字。
170. 作为已认证用户，我希望通过 MCP 查询员工的使用能力画像，版本与数值和 Web 相同，以便在 Agent 中获得同样的结论与依据。

### 守则与运行

171. 作为员工，我希望等待数据不被用于考勤、不折算工时、不触发超时提醒，以便平台不变成监工工具。
172. 作为管理者，我希望平台不根据评估结论自动发送通知或触发任何人事动作，以便结论只作为人工判断的参考。
173. 作为平台维护者，我希望所有指标都能从原件全量重算，且结果与增量计算一致，以便修正口径或解析错误后数据可以恢复。
174. 作为平台维护者，我希望 Web、MCP 与导出使用同一个指标服务，以便不同入口不出现不同数字。
175. 作为平台维护者，我希望客户端拿不到“本轮结束”或“权限请求”事件时，相关指标显示“未知”，而不是用启发式猜测，以便不引入伪精确数据。
176. 作为已认证用户，我希望所有页面都满足以下要求，以便在任何设备上都能无障碍使用：
     - 320—1920 px 宽度下可用，没有横向滚动
     - 浅色与深色主题对比度达标
     - 提示层可以用键盘访问

## Implementation Decisions

### 1. 前置条件与范围变更

- **数据基础与本轮执行顺序（2026-10-03）：** V2 的指标全部建立在 V1 的原件、规范化事件与分析结果之上，仓库已有这条数据链。
  - 原顺序要求 G2/G3 通过后才写 V2 代码，未通过时仅做 S0。用户本轮直接要求“开始实现V2”，现据此先开发，并将 S0 文档随首批实现交付审阅。
  - 本轮指示调整开发顺序，不代表 G2/G3 或其余 V1 门槛已通过，也不代表用户已经审阅本次 S0 修订文本。
  - V1 未验收项继续保留，V2 发布仍须满足本 PRD 的发布门槛和 V1 回归。实际状态以 V1 验收台账为准。
  - 产品页面读取已提交原件的派生数据；验证通过公开产品入口注入合成材料，不用无来源的页面假数据代替数据链。
- **范围变更已由用户确认（2026-09-28）：** 引入使用能力评估，即综合指数、等级分组和员工画像。它修订了以下既有约定：
  - PRD v1.0 的 US 71、§5 中“不产生 AI 绩效分数或排名”，以及 Out of Scope 中的“自动绩效评分、员工排名”
  - 术语表中「绩效参考」的定义
  - V2 实现提示词第六节守则第 1 条与 AC-28
- **修订后的边界：**
  - 允许基于已采集的会话，按固定锚点给出 Coding Agent 使用能力的等级与综合指数。
  - 仍然不产生整体绩效分。
  - 不提供名次、榜单或按分数排序的人员列表。
  - 不折算工时，不做考勤。
- **S0 文档工作（本轮随首批实现交付审阅，文档签收状态单独记录）：**
  1. 新增 ADR-0004，记录引入 V2 报表与使用能力评估的决定和守则，以及被否决的做法：
     - 名次与 Top / Bottom 榜单
     - 同事之间的百分位排名
     - 工时折算与考勤
     - 根据结论自动触发人事动作
     - 用户自定义权重
  2. 更新术语表：修订「绩效参考」的定义，并新增以下术语：
     - 使用能力评估、员工画像
     - 活动记录、对话视图
     - 组装记录、等待回复、权限等待
     - 复核备注
  3. 修订 PRD v1.0 中 US 71、§5 与 Out of Scope 的措辞，指向本 PRD；在 V1 验收标准的 AC-13 与第 7 节注明评分条款已由本 PRD 修订。
  4. 在 V2 实现提示词中注明：第六节守则第 1 条与 AC-28 已被本 PRD 取代。
- **可见范围：** 沿用 ADR-0002，所有已认证用户都能查看全部报表、评估、员工画像与复核备注。V2 不引入角色或按人读取的控制。该决定由用户于 2026-09-28 确认。

### 2. Module 与 Interface

沿用 V1 的模块化单体与 Module 边界。新增能力放进已有 Module，不新增独立部署单元。Web 与 MCP 继续调用同一个 Reporting / Evidence Interface，不分别计算事实。

| Module | 新增或扩展的 Interface | 隐藏的 Implementation / 约束 |
| --- | --- | --- |
| Archive / Evidence | `readAssembly`、`listAssembly`、`readPipeline` | 组装与去重过程中写入审计记录；不修改原件；谱系无法确定时保持分离 |
| Evidence | `readConversation`（分页，可选包含工具调用）、`queryActivity`（分页、筛选） | 从规范化事件投影轮次边界、等待区间、权限等待、并行标记与特殊内容标识；客户端拿不到的事件标“未知” |
| Analysis | 扩展结构化输出 | 任务类型、提示词要素、返工、追问、已验证 / 仅声称、写法建议；每一项都带证据位置与分析版本；旧任务的结果不覆盖新版本 |
| Reporting · 指标服务 | `readMetrics(scope)`、`readSessionMetrics`、`readMetricCatalog`、`recompute(scope)` | 唯一计算指标的地方；按会话与快照代次物化，支持增量更新与全量重算；日、周、人的汇总等于会话级之和（已知部分） |
| Reporting · 使用能力评估 | `listCapability(period, preset)`、`readCapability(employee, period, preset)`、`readCapabilityTrend`、`addReviewNote`、`listReviewNotes` | 模型参数版本化；结果按员工、范围、方案、模型版本与输入版本物化并追加版本 |
| Reporting · 更正 | 扩展 `correct` | 可以更正任务类型、提示词要素和返工判定；更正后重算指标与评估，保留旧版本与操作者 |
| Web | 新页面与共用组件 | 共用筛选条、图表与表格双视图、设计令牌 |
| MCP | 新增查询工具 | 与 Web 使用同一服务、同一版本，返回同一数值 |

- **scope 的组成：** 时间范围，以及可选的员工、Agent、项目。
- **时间范围：** 报表与评估统一提供本周、上周、接入至今。
  - 周按北京时间计算，从周一到周日。
  - 评估范围的起点不早于该员工的接入日期。
- **MCP 新增工具：**
  - 查询：`get_report_summary`、`list_activity`、`read_conversation`、`get_metric_catalog`、`get_capability_profile`
  - V1 的 `search_sessions` 结果增加对话消息命中，可以定位到具体消息
  - 分页与单次响应大小限制沿用 V1 的 Interface 约定

### 3. 指标口径（唯一定义，Web、MCP、导出共用）

| 指标 | 定义 | 来源与级别 |
| --- | --- | --- |
| 会话 | 有事件的会话，含子会话；按来源时间归期；续聊合并为同一会话 | 原件 · 确定性 |
| 提示词（用户轮次） | 用户提交的消息，不含工具结果与压缩摘要 | 原件 · 确定性 |
| 首条提示词 | 每个会话中用户的第一条提示词 | 原件 · 确定性 |
| 工具调用 | Agent 发起的工具调用次数 | 原件 · 确定性 |
| Token 输入 / 输出 | 客户端记录的用量；未上报标“未知”，不计为 0，不进入比值 | 原件 · 确定性 |
| 代码变更行 | 会话内 Edit / Write / apply_patch 等工具的增删行 | 原件 · 确定性 |
| 测试运行 / 通过 | 从工具输出中解析出的测试运行与通过次数；不采信 Agent 陈述 | 原件 · 解析 |
| 会话内提交 | 会话中执行的 git commit | 原件 · 确定性 |
| 已验证结果 | 报告中有工具结果佐证的结果条目 | 模型提取 + 证据核对 |
| 仅声称 | 只有用户或 Agent 陈述、没有工具结果的结果条目 | 模型提取 |
| 产效比 | 已验证结果 ÷ 百万 Token（已知）；只在同类任务之间参考 | 派生 |
| 代码产出 | 代码变更行 ÷ 百万 Token（已知） | 派生 |
| 等待占比 | 等待回复与权限等待的时长 ÷ 会话活跃区间 | 派生 |
| 任务类型 | 实现 / 修复 / 排查 / 重构 / 测试 / 运维 / 整理；可以更正 | 模型推断 |
| 提示词要素 | 目标、约束、上下文、验收标准是否出现 | 模型推断 |
| 返工率 | 纠正或推翻上一轮结果的提示词 ÷ 非首条提示词 | 模型推断 + 规则 |
| 无返工会话 | 整段会话没有返工提示词 | 模型推断 + 规则 |
| Agent 追问率 | Agent 向用户澄清需求的次数 ÷ 提示词 | 模型推断 |
| 等待回复 | Agent 本轮结束（等待输入）到用户下一条消息的间隔；会话最后一次回复之后的空闲不计 | 原件时间戳 · 确定性 |
| 权限等待 | Agent 发起命令确认到用户批准或拒绝的间隔 | 原件时间戳 · 确定性 |
| 期间在别处工作 | 等待期间，同一员工在其他会话中有事件 | 原件时间戳 · 确定性 |
| 活跃天数 | 所选范围内有会话事件的工作日数；工作日为周一至周五 | 派生 |

- **事件可得性：** 各客户端能否识别“本轮结束”和“权限请求”，取决于 Adapter 实际能拿到的事件。
  - 逐个客户端核实后写入口径文档。
  - 拿不到的显示“未知”，不用启发式猜测后当作确定值。
- **长等待阈值：** 等待回复 ≥ 10 分钟为长等待；权限等待 ≥ 3 分钟会进入活动记录。

### 4. 会话组装审计

- 每个会话都有一份组装记录，内容包括：
  - 来源文件与快照代次、分块数
  - 各类去重的条数与原因
  - 谱系决策、组装状态
  - 完成时间、组装规则版本
- 各字段的取值：
  - **去重原因：** 网络重试或重复投递、续聊复制的历史、压缩摘要派生内容。
  - **谱系决策：** 续聊合并、子会话侧链、离线补传并入、无法确定而保持分离。
  - **组装状态：** 已组装、组装中、存在缺口、待确认谱系。
- 判定沿用 V1 的规则：按来源会话身份、文件代次、原件位置和谱系识别重复；不能只凭文本相同就合并两次真实活动。组装决策写入审计记录，不修改原件。
- “数据处理”页展示以下内容：
  - 当日链路计数：拾取 → 接收分块 → 去重 → 组装 → 解析与指标 → 报告
  - 原文可见延迟 P95
  - 组装记录表（可按状态筛选）
  - 去重规则说明
  - 待确认谱系列表及原因
  - 数据质量：各 Agent 的 Token 上报覆盖率
  - 指标口径表
- 会话详情侧栏的“组装与去重”面板，展示该会话的组装记录。

### 5. 对话视图与活动记录

- **对话视图**（会话详情的默认视图）：
  - **消息与工具调用：**
    - 用户与 Agent 的消息顺序与原件一致。
    - 工具调用默认隐藏、可以展开；隐藏时在下一条 Agent 消息上注明“N 次工具调用（已隐藏）”。
  - **等待标注：** 两条消息之间显示等待回复时长，≥ 10 分钟的高亮，并标注“期间在其他会话中活动”。
  - **特殊内容标识：**
    - 需要标识的内容：接入前旧内容（续聊同步）、离线补传、上下文压缩、采集缺口、进行中。
    - Agent 自述但没有工具结果佐证的，标“无工具结果佐证”。
    - 消息原文只展示，不改写。
  - **切换与跳转：**
    - 保留 V1 的时间线与原件 JSONL 视图。
    - 证据锚点跳到时间线的原位置，对话锚点跳到对应消息并高亮。
    - 子会话以链接出现。
    - 长会话分页加载。
- **活动记录**（新页面）：
  - 按北京时间逐条记录以下事件：
    - 会话开始与结束
    - 提问（区分返工提问）、Agent 回复与追问
    - ≥ 10 分钟的等待、≥ 3 分钟的权限等待
    - 上下文压缩、采集缺口、离线与补传
  - 每条显示时间点、员工、会话、Agent、项目和原句摘录；摘录被截断时标注省略号。
  - 可以按日期、员工、Agent、项目、事件类型筛选；点击后跳到对话中的原句。
  - 页面上方是当天的“对话节奏”泳道图：
    - 每名员工一行，会话条按 Agent 着色
    - 提问为点，返工提问为空心点
    - 长等待为浅灰段
    - 另有一条“现在”线
  - 迟到数据按来源时间归期，并标“补传”。

### 6. 报表页

- **所有报表页共用的要求：**

### 7. 使用能力评估模型

**评估对象：** 一名员工在所选范围内已采集的会话。它回答的问题是：这名员工用 Coding Agent 完成工作的方式与效果如何。它不代表整体绩效，也不覆盖会议、评审和不借助 Agent 的工作。

**维度、指标与锚点（初始参数）：**

| 维度 | 回答的问题 | 指标 | 0 分 → 100 分 | 最少样本 |
| --- | --- | --- | --- | --- |
| 使用深度 | 是否把 Agent 用进日常工作 | 活跃天数占比 = 有会话事件的工作日 ÷ 范围内接入后的工作日 | 30% → 90% | 1 个工作日 |
| 使用深度 | 同上 | 活跃日会话数 = 会话数 ÷ 活跃天数 | 0.6 → 1.8 | 1 个活跃日 |
| 需求表达 | 提示词是否写清楚 | 首条提示词要素覆盖 = 各会话首条提示词中目标、约束、上下文、验收四项出现率的平均值 | 30% → 75% | 3 条首条提示词 |
| 需求表达 | 同上 | Agent 追问率 | 20% → 3% | 3 条提示词 |
| 迭代效率 | 来回修改多不多 | 返工率 | 28% → 5% | 3 条非首条提示词 |
| 迭代效率 | 同上 | 无返工会话占比 | 20% → 85% | 3 个会话 |
| 迭代效率 | 同上 | 每条已验证结果的轮次 = 提示词数 ÷ 已验证结果（为 0 时按 0.5 计） | 14 → 3 | 3 条提示词 |
| 验证把关 | 结果有没有经过验证 | 已验证占比 = 已验证 ÷（已验证 + 仅声称） | 50% → 95% | 4 个结果条目 |
| 验证把关 | 同上 | 运行测试的会话占比，只看实现、修复、重构、测试类会话 | 15% → 80% | 3 个会话 |
| 产出转化 | 投入是否变成可核对的结果 | 已验证结果指数 = 各已结束会话的已验证结果 ÷ 团队同类任务均值，取平均 | 0.5× → 1.4× | 3 个已结束会话 |
| 产出转化 | 同上 | 产效比指数 = 各已结束会话的产效比 ÷ 团队同类任务中位数，取平均 | 0.5× → 1.5× | 3 个 Token 已知的已结束会话 |
| 协作节奏 | Agent 是否常被卡住 | 权限等待中位数 | 6 分钟 → 0.8 分钟 | 3 次权限等待 |
| 协作节奏 | 同上 | 10 分钟以上等待占比，期间在其他会话中活动的等待不计 | 35% → 5% | 3 次等待 |

**计算规则：**

1. **指标得分** = (值 − 0 分锚点) ÷ (100 分锚点 − 0 分锚点) × 100，截断到 0—100。越低越好的指标，锚点是递减的。
2. **样本不足：** 单项样本少于上表的最少样本时，该指标不计分，显示“样本不足”。
3. **维度得分** = 该维度可计分指标的平均值；所有指标都不可计分时，维度显示“样本不足”。
4. **综合指数** = 各维度得分按权重方案加权平均。样本不足的维度不参与计算，其权重按比例分给其他维度。结果取整数。
5. **等级**按取整后的综合指数判断：
   - ≥ 72：较好
   - 60—71：一般
   - < 60：需提升
6. **可信度：**
   - 会话 ≥ 8 且提示词 ≥ 40 为高；会话 ≥ 5 且提示词 ≥ 25 为中；其余为低。
   - 任一客户端待信任，或范围内存在采集缺口时，可信度降一级。
   - 可信度为低时，等级显示“待定”，综合指数只作参考。
7. **误差**显示为 ±round(26 ÷ √会话数)，标注为估计值。
8. **强项与优先提升：**
   - 强项取取整后 ≥ 70 的维度，按得分最多列两个。
   - 优先提升取取整后 < 60 的维度，按得分从低到高最多列两个。
   - 总结句中注明低于 60 分的维度总数。
9. **辅导建议**来自固定建议库，不由模型即时生成：
   - 按优先提升的维度选取建议。
   - 需求表达维度按出现率最低的提示词要素选取。
10. **代表性会话：**
    - 最佳示例：在有已验证结果且无返工的已结束会话中，取已验证结果最多的一个；数量相同时取 Token 较少的。
    - 返工较多的会话：取“返工次数 + 仅声称 − 已验证”最大的会话。
11. **团队中位数**：同一范围、同一方案下各员工维度得分的中位数。它只作为画像中的参照，不参与任何人的评分。
12. **产出转化的基线：**
    - 取团队同类任务已结束会话的已验证结果均值（下限 0.5）与产效比中位数。
    - 初始窗口为接入至今。
    - 基线版本随评估结果一起记录。
    - 因此这个维度会随团队整体水平变化；其余维度只看本人数据。

**权重方案（系统提供，用户不可自定义）：**

| 方案 | 使用深度 | 需求表达 | 迭代效率 | 验证把关 | 产出转化 | 协作节奏 |
| --- | --- | --- | --- | --- | --- | --- |
| 默认 | 20 | 20 | 20 | 20 | 15 | 5 |
| 重产出 | 15 | 15 | 15 | 15 | 35 | 5 |
| 重质量 | 10 | 25 | 25 | 30 | 10 | 0 |

**初始建议库：**

| 维度或要素 | 建议 |
| --- | --- |
| 使用深度 | 把排查、补测试、整理文档这类日常任务也交给 Agent，保持每个工作日都在用 |
| 迭代效率 | 动手前让 Agent 先复述方案并确认；把不能改动的范围写进第一条提示词 |
| 验证把关 | 要求 Agent 运行测试并贴出结果；对“已验证”“已通过”的说法追问证据 |
| 产出转化 | 把任务拆小，每个会话以一个可验证的结果收尾（测试通过或提交） |
| 协作节奏 | 把 git diff、测试等只读命令加入允许列表，减少 Agent 等待批准 |
| 需求表达 · 目标 | 第一句写清要达成的目标 |
| 需求表达 · 约束 | 写明不能改动的文件、接口或环境 |
| 需求表达 · 上下文 | 附上文件路径、报错日志或复现步骤 |
| 需求表达 · 验收 | 写明怎样算完成，例如要跑哪些测试 |

**版本与重算：**
- **模型参数整体版本化：** 锚点、样本门槛、权重方案、等级阈值、可信度门槛与建议库作为一个整体记录版本。
- **每个评估结果记录：** 模型版本、指标版本、所用分析版本、基线版本与生成时间（北京时间）。
- **何时生成新版本：** 输入变化（迟到数据、更正、重新分析）或模型版本变化时，生成新的结果版本。
  - 旧版本保留，可以查询。
  - 旧任务不覆盖新版本。

**结果形状**（来自原型的评估函数，只保留与决策相关的字段）：

```ts
type Level = '较好' | '一般' | '需提升' | '待定';
type DimKey = 'adopt' | 'prompt' | 'iter' | 'verify' | 'output' | 'flow';

interface MetricScore {
  key: string;                       // 例如 rework、verShare
  value: number | null;              // 原始值；样本不足时为 null
  anchor: [zero: number, full: number]; // 0 分与 100 分对应的值，可以递减
  score: number | null;              // 线性折算并截断到 0–100
  samples: number;
}

interface CapabilityAssessment {
  employee: string;
  period: string;                    // 自然周（如 2026-W39）或“接入至今”
  preset: '默认' | '重产出' | '重质量';
  modelVersion: string;
  inputs: { metricsVersion: string; analysisVersions: string[]; baselineVersion: string };
  index: number | null;              // 0–100 的整数；分档按这个显示值判断
  margin: number | null;             // ±，按会话数估计
  confidence: '高' | '中' | '低';
  level: Level;                      // 可信度为低时为“待定”
  dims: Record<DimKey, { score: number | null; metrics: MetricScore[] }>;
  strengths: DimKey[];               // 取整后 ≥ 70，最多 2 个
  priorities: DimKey[];              // 取整后 < 60，最多 2 个
  tips: { dim: DimKey; text: string }[];
  sample: { sessions: number; prompts: number; activeDays: number; workdays: number; unknownTokenSessions: number };
  coverageIssues: string[];          // 例如“Codex Desktop 待信任”
  generatedAt: string;
}
```

### 8. 员工一览与员工画像

- **员工一览：**
  - **顶部控制：** 评估范围（本周 / 上周 / 接入至今）与权重方案（默认 / 重产出 / 重质量），与员工画像共用同一组控制。
  - **结论区：** 较好、一般、需提升、待定四组，每组显示：
    - 人数与说明
    - 员工姓名、综合指数与一句理由
    - 组内按姓名排列
  - **守则提示：** 采用固定锚点、按任务类型校正、样本不足不评级、结论需要人工复核。
  - **员工卡片：**
    - 姓名、角色、等级
    - 综合指数、±误差、可信度
    - 六个维度的得分条
    - 会话、提示词、已验证结果与返工率
    - 覆盖警示
    - 整张卡片可以点击进入画像
  - **评估方法与口径说明：** 可展开，列出维度、指标、锚点、当前权重、等级、可信度、公平校正与用途。
- **员工画像：**
  - **页头与控制：**
    - 页头显示姓名、角色、设备数、最近同步与接入日期。
    - 可以在“画像 / 日报 / 周视图”之间切换，另有范围与方案控制。
    - 目录在宽屏上吸顶。
  - **页面依次包含以下各节：**
    1. **结论**：
       - 等级、综合指数、误差、可信度
       - 一句总结，注明依据的会话与提示词数量
       - 覆盖提示
       - 强项、优先提升与辅导建议
    2. **能力维度**：
       - 每个维度显示本人得分条与团队中位数刻线。
       - 展开后显示各指标的原始数值、锚点、得分与样本数。
       - 低于 60 分的维度默认展开。
    3. **使用数据**：
       - 活跃天数、会话与提示词、已知 Token、已验证结果、代码变更与测试
       - 每日会话、每日 Token、每日已验证结果三张小图
       - 使用的 Agent 与任务类型分布
    4. **工作内容**：来自日报与周报的工作主题与记录到的阻塞。
    5. **协作方式**：
       - 提示词写法：
         - 首条提示词各要素的出现率，与团队水平对比
         - 返工率、追问率、无返工会话占比、提示词中位长度
         - 代表性会话与返工较多的会话，都可以跳到原句
       - 响应与等待：
         - 等待回复的中位数、P90、10 分钟以上的占比、期间在别处工作的占比
         - 权限等待中位数、各时段的等待中位数
         - 停得最久的权限请求
    6. **会话**：所选范围内的会话明细。
    7. **最近活动**：最近的活动条目，可以跳到带好筛选条件的活动记录。
    8. **趋势**：上周 → 本周的综合指数与各维度变化，用哑铃图表示；上周没有会话时明确提示。
    9. **复核备注**：追加式，记录作者与时间，不改变评估数据。
  - **待定：** 结论写明原因（样本不足、客户端待信任），各维度只作参考。
  - **范围内没有会话：** 显示空状态，提示换一个范围。

### 9. 守则（V2 修订版）

1. **唯一允许的综合指数：** 使用能力评估是唯一允许的综合指数。
   - 它只评价用 Coding Agent 工作的方式与效果。
   - 不合成整体绩效分，也不作为考勤或工时依据。
2. **不排名：**
   - 不提供名次、Top / Bottom 榜单、同事之间的百分位排名。
   - 不提供按综合指数或单项指标排序的人员列表，也不提供这类导出。
   - 人员表与评估分组内固定按姓名排列。
   - 会话明细表可以排序。
3. **比值要拆开：** 比值同时展示分子与分母，注明“只在同类任务之间参考”；Token 未知的会话不参与比值。
4. **未知不等于 0：**
   - 未上报的字段显示“未知”，不画成 0，不进入趋势线。
   - 合计写成“已知部分 + N 个会话未知”。
5. **证据分级：**
   - 推断字段标注“模型推断”，可以更正、重算，并保留版本。
   - “已验证”只计有工具结果佐证的条目。
6. **等待不等于怠工：**
   - 不折算工时，不做考勤，不设超时惩罚类提醒。
   - 长等待旁同时显示“期间在其他会话中活动”。
   - 权限等待单列，定位为流程问题。
7. **人工复核：**
   - 评估结论是辅导与经验分享的参考，需要人工复核。
   - 平台不因评估结论发送通知、提醒或触发任何人事动作。
   - 员工与管理者都可以追加复核备注。
8. **公平与透明：**
   - 固定锚点，按任务类型校正，样本门槛与可信度门槛不足时不评级。
   - 每个分数都能展开到原始数值、锚点与原文。
   - 方法说明随页面提供。
9. **同源可重算：**
   - 所有报表、评估、MCP 与导出都来自同一个指标服务。
   - 可以从原件重算。
   - 页面标注数据截至时间，并链接口径。
10. **沿用 V1：**
    - 分析 Worker 不执行原文中的指令。
    - 系统分析会话不计入员工活动。
    - 认证后共享查看。
    - 原件不可覆写。
11. **不伪造数据：** 测试只用合成会话；界面不出现无来源的数字。

### 10. 界面与可视化规范

- **设计令牌：** 沿用原型确定的设计令牌与字体角色。
  - 亚麻色底、玉兰白面板、午夜蓝墨色，矢车菊蓝只用于焦点、选中与“今天”。
  - Geist 用于界面，Noto Serif SC 用于分析叙述，Geist Mono 用于原件。
- **图表配色：** 以下颜色已在浅色与深色下校验。
  - 浅色：#3d8ce6、#e36d24、#16a08f、#7a5bd3
  - 深色：#3f8fe6、#dd7230、#1ca894、#8a74e2
  - 连续色阶为 8 级，每一级单独指定文字颜色。
- **图表规范：**
  - 细标记，2px 间隙，发丝网格。
  - 提示层“值在前、标签在后”，键盘可达。
  - 散点图最多 3 种颜色，其余用强调色或灰色参照。
  - 不用双 y 轴。
  - 每张图都有表格视图。
- **能力维度的画法：**
  - 本人得分用主色条，团队中位数用墨色刻线。
  - 趋势用哑铃图：上周为灰点，本周为主色点。
- **无障碍与适配：**
  - 320—1920 px 无横向滚动。
  - 触控目标 ≥ 44 px。
  - 浅色与深色对比度达标。
  - 遵守“减少动效”偏好。
  - 时间一律为北京时间。

## Testing Decisions

### 测试 Seam（2026-09-28 与用户确认）

沿用 V1 的原则：通过公开 Interface 与可见状态断言结果，不新增专为测试绕过产品流程的入口。

1. **主 Seam：服务端业务边界，上传契约进，Reporting 查询出。**
   - **输入：** 合成的原生会话原件（Claude Code / Codex JSONL），经设备上传契约（`acceptChunk`、`commitManifest`）进入，与真实采集器走同一条路径。
   - **输出：** 通过 Web、MCP 与导出共用的 Reporting / Evidence 查询 Interface，断言以下结果：
     - 指标、对话、活动记录
     - 组装记录、报告
     - 使用能力评估与员工画像
   - **一致性：** 同一范围下核对 Web、MCP、导出三个入口的数值一致；核对从原件全量重算的结果与增量结果一致。
   - **故障注入：** 在这个 Seam 上注入以下情况：
     - 重复分块、ACK 丢失后的重试
     - 续聊复制、上下文压缩
     - 子会话、离线补传
2. **Analysis Seam（沿用 V1）：**
   - 用确定性的分析替身代替 Claude Code Worker。替身返回符合 schema、带证据位置的推断字段：
     - 任务类型、提示词要素
     - 返工、追问
     - 已验证 / 仅声称
     - 写法建议
   - 推断输入被固定下来后，指标与评估可以精确断言。
   - 真实的 Claude Code + 千问链路单独验收：只断言结构、证据与不越界行为，不比对文本。
3. **界面验收 Seam：**
   - 用浏览器端到端测试，只覆盖界面独有的行为：
     - 每张图都能切换到表格视图
     - 提示层可用键盘访问
     - 320—1920 px 下没有横向滚动
     - 浅色与深色对比度达标
     - 锚点跳到正确的原句
     - 人员表按姓名固定排列，页面上没有任何排名界面
   - 被测服务通过主 Seam 注入合成数据。

测试不断言内部表名、物化方式、缓存，或某个辅助函数是否被调用。

### 好测试的标准

- **合成会话 + 事先算好的期望：**
  - 每个合成员工按预设的使用习惯生成会话，例如验证习惯、返工倾向、提示词要素出现率、权限等待。
  - 期望值事先手工算出。
  - 原型中六位合成员工的差异化使用画像，可以作为设计合成样例的参考。
- **断言可观察的行为：** 数值、状态、版本、跳转位置，以及“未知”“样本不足”“待定”等标识。不以实现与测试代码相似作为正确性的证明。
- **边界表：**
  - 锚点两端与截断
  - 取整分档：71.4 → 71，一般；71.5 → 72，较好
  - 样本门槛：2 个样本与 3 个样本
  - 客户端待信任时可信度下调
  - 缺失维度的权重重分配
  - 切换权重方案时维度得分不变
- **守则是可测的负向断言：**
  - Interface 与导出中不存在名次字段或按分数排序的参数。
  - 人员顺序固定。
  - 页面不出现考勤或超时惩罚类的表述与提醒。
  - 评估变化不产生任何通知。
- **故障注入只改变外部条件或已定义的契约。**
- **只用合成数据**，不读取真实员工材料。

- **被测对象：**
  - Evidence：对话、活动记录、组装记录
  - Reporting：指标服务、使用能力评估、更正与复核备注
  - Analysis：扩展后的输出
  - Web 与 MCP 入口
- **现有基础（2026-10-03）：**

## Out of Scope

- 整体绩效分，以及把评估作为人事决策的自动依据；根据评估结论自动发送通知、提醒或触发任何人事动作。
- 名次、Top / Bottom 榜单、同事之间的百分位排名、按综合指数或单项指标排序的人员列表，以及包含排名的导出。
- 工时折算、考勤、超时惩罚类提醒。
- 用户自定义权重、锚点或阈值；V2 只提供三套系统方案，参数调整走版本发布。
- 按团队或员工隔离读取的角色体系（沿用 ADR-0002）。
- 报表与评估的任意自定义日期范围；V2 只提供本周、上周与接入至今。
- 人工确认或合并谱系的操作；V2 只展示待确认列表与原因。
- 跨组织或行业基准对比。
- 法定节假日日历；工作日暂按周一至周五计算。
- 衡量不使用 Agent 的工作；评估只覆盖已采集的会话。
- PRD v1.0 已列的范围外事项继续有效，例如：外部 Git / PR / issue / CI 关联、批量导入历史会话、恢复代码工作区、精确人工工时。

### 初始参数与校准

- **来源：** 锚点、样本门槛、权重、等级阈值、可信度门槛和误差估计，都来自原型在合成数据上的校准，是初始值。
- **校准示例：** 在原型的六位合成员工上，按“接入至今、默认方案”得出：
  - 较好：两人
  - 一般：两人
  - 需提升：一人
  - 待定：一人（样本不足，且客户端待信任）
- **后续复核：** 试点后用真实分布复核参数。调整以新模型版本发布，旧结果保留。误差区间可以改用自助法（bootstrap）标定。

### 已知局限

- 评估只看已采集的会话，不覆盖会议、评审和不使用 Agent 的工作；客户端覆盖不完整会降低可信度。
- 产出转化维度以团队同类任务为基线，会随团队整体水平变化。
- 提示词要素、返工、追问、任务类型和已验证判定来自模型推断，可能出错；可以更正并重算。
- 单周样本通常较少，本周与上周的评估多为中、低可信度，趋势只看方向。
- 各客户端能否提供“本轮结束”与“权限请求”事件需要逐一核实；拿不到时相关指标为“未知”，协作节奏维度可能缺失。

### 待确认事项

- AC-32 性能目标已于 2026-10-04 确认，见验收表；测试报告须说明实际环境与测量条件。
- 工作日是否扣除法定节假日。
- 产出转化基线的时间窗口，初始为接入至今的全部已结束会话。

### 原型与实施约束

- 仓库中的 Web 平台原型（`prototypes/web-platform/`）演示了全部页面与交互，数据为合成。它只作界面与口径参考，代码不进入产品。如果仓库中没有这个目录，向用户索取原型分支。
- 实现时只用合成数据，不读取真实员工材料。
- 发现冲突时先按本 PRD 的覆盖关系与当前用户指示处理；未被覆盖的新产品取舍列出具体差异供用户决定。
