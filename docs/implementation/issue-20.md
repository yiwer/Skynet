## 使用路径

服务器离线 `provision` 入口增加可选布尔字段 `canManageIdentities`，省略时为 `false`。已有账号迁移后也默认为无维护权限。显式创建维护账号的输入示例：

```json
{"name":"身份维护者","canManageIdentities":true}
```

通过原有 `npm run provision` 标准输入传入，使用运维环境中的 `DATABASE_URL`；输出的 `readerCredential` 用于登录 Web。没有默认维护账号或默认凭据，HTTP 接口不能授予维护权限。普通账号仍按原有 `{ "name": "员工姓名" }` 创建。设备上传凭据、个人接入授权值均不能作为读取或维护凭据。

维护者登录后进入“接入与设备”。列表显示账号状态、各设备自身状态和受账号停用影响后的实际上传状态。停用前说明影响并要求确认；请求失败保留确认入口以便重试，成功显示结果。重复停用返回相同停用状态，不重复生成维护记录。账号和记录列表分页显示。

停用一个设备，只拒绝该设备后续上传和快照提交。同员工其他设备、读取身份及个人接入授权值仍可使用。停用账号则拒绝该员工所有后续读取、原件/可读/恢复包下载、设备注册和所有设备上传。已登录页面在下一次请求收到 401 后清除会话与已展示材料，回到登录页。服务端按每次请求查询有效状态，不依赖登录时缓存的权限。

停用不会删除原件、快照、设备或员工归属。其他有效读者依然能查看所有员工和项目，也能下载已停用员工的历史材料；查看范围不因维护权限改变。停用只影响后续服务请求，已完成的下载不会被撤回。

## 公开接口与边界

| 接口 | 权限与结果 |
| --- | --- |
| `GET /api/me` | 有效读取身份；增加 `canManageIdentities`，默认 `false` |
| `GET /api/identities?offset=0` | 有效维护身份；账号、设备及实际有效状态，每页 50 个账号 |
| `GET /api/identity-audit?offset=0` | 有效维护身份；操作人、目标账号/设备、动作与时间，每页 50 条 |
| `POST /api/identities/employees/:id/disable` | 有效维护身份；空 JSON 请求体，停用指定账号 |
| `POST /api/identities/devices/:id/disable` | 有效维护身份；空 JSON 请求体，停用指定设备 |

停用响应为 `{id,kind,active:false,changed}`；已经停用时 `changed:false`。匿名、上传凭据及已停用身份返回 401；无维护权限的有效读者返回 403；不存在的目标返回 404。客户端不得提交维护权限、上传归属或审计操作人，额外字段按严格请求契约拒绝。

身份校验集中在 `apps/server/identities.ts`，所有现有存档读取和设备上传入口继续调用同一 guard。停用与审计写入在一个事务内完成，锁定操作人有效身份和目标状态；并发重复请求至多记录一次实际状态变更。审计持久保存操作人 ID、目标员工/设备 ID、动作及服务端时间，响应不包含凭据原文或凭据哈希。没有新增角色层级、在线授权或启用接口。

```sh
npm ci

```

`tests/identities.test.ts` 通过离线公开入口创建两个员工、每人两台设备及一个明确授权的维护者，使用产品 HTTP 接口与 Playwright Web。全部会话为合成材料，无真实员工会话或凭据。验证包括：

- 默认无维护权限，设备凭据不能读取/维护；匿名、普通读者越权及伪造员工归属/操作人被拒绝。
- 两个普通员工可交叉读取所有项目，维护者拥有的上传凭据也不能用于维护。
- Web 停用设备的服务失败提示与重试；被停用设备拒绝上传和停用前已暂存原件的后续提交，另一设备继续成功上传，账号仍能读取与注册新设备。
- Web 停用账号后，两个已有登录页面分别在刷新和下载时退出；全部读取/导出路由、原设备与新设备上传、个人授权值注册均被拒绝。
- 另一员工的两台设备保持可用；其读取身份仍能下载停用员工的原件、可读导出和恢复包，原件逐字节一致且历史归属保留。
- 并发重复操作不产生重复审计；操作人、目标与时间正确，结果不暴露任何测试凭据或哈希；服务器重启后状态、审计与历史仍存在。
