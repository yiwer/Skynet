# #54 画像固定指标准备切片

范围：只减少当前员工画像的一次重复指标准备，属于 #54 的局部优化，不代表性能验收完成。

画像已经通过当前评估取得固定 Usage 及其 `metricVersion`。此前随后调用员工产效入口，重新准备相同周期的团队 Metrics，再计算员工 Usage 和产效。现在把前一步固定指标版本传给 `usage.forMetric`，沿用原来的员工 Usage 计算，再由 `efficiency.exportFromMetric` 计算产效；公开 HTTP、MCP、版本和筛选合同均不增加参数。

## 保持的边界

- 固定指标读取验证原来的周期、来源、项目等完整筛选。Usage 原本读取团队指标作为员工与团队对照的基础，因此仅移除员工选择再读取固定指标；实际员工投影仍由原计算器执行，不把团队输出总量直接放进员工结果。
- 当前画像先正常读取当前评估及 Usage，仍核验原件。复用边界只读取该次准备所得的固定指标版本，不保存跨请求字节、结果或 TTL 缓存。后续洞察、归属、原生计时与等待准备照常执行。
- 全量画像先执行 `assessments.recompute`，其上游已重算 Metrics。随后固定指标投影继续传递 `full`，让洞察与计时重算；不会再次重算同一 Metrics。已有外层 `consistentReportingInputs` 保证迟到、归属、更正和跨日变化触发重试，不能保存混合输入画像。
- 固定历史画像继续从原有不可变版本读取。没有更换版本算法、未知口径、资源上限或原件校验规则。

未采用直接改写团队 Usage 的 `selected` 标记：团队每日产出包含全部产出种类，而员工每日摘要只有部分字段，这种改写会遗漏日期和产出，导致员工版本与独立入口不等价。本切片复用完整原计算路径。

## 公开测试与性能证据

`tests/profile-preparation.test.ts` 经公开上传与分析结果边界建立两名员工、跨周数据，验证接入至今/本周/上周的员工范围、Token、产出、完整产效版本、固定 Usage 身份、全量重算一致性；迟到新原件生成新画像，旧三周期版本保持不变。已有 unknown 用例覆盖日期不可确定的原件不当作空员工零值。

最终构建通过。新增周期等价与既有 unknown 两条公开回归通过（35.20 秒）；已有画像 HTTP、OAuth MCP、分页、跨日、投递、重启及历史版本九条通过（160.67 秒）。补充人工更正回归通过（14.78 秒）：返工更正同时影响画像、评估和独立产效，同版引用一致，全量重算与当前相等，历史保持。共 12 条语义回归通过。

独立性能命令：`node --import tsx tests/profile-preparation-performance.ts`。使用隔离合成的 3 名员工、36 会话、2,880 个用户轮次；每轮当前读检查员工 12 会话/960 轮次/12,000 输入 Token 与未分析产出未知，再检查固定版本和全量重算完全相等。它有显式 1 秒后续读取阈值，未加入默认必须绿色的测试套件。

优化前公开 RED：首次 9,504 ms，后续三次 7,702/5,797/7,696 ms，后续 P95 7,702 ms，全部数据与版本断言通过后因时限失败。该小样本只用于诊断重复准备，不符合 AC32 的 10 人/4 周/1,000 会话规模；共享开发机负载也会改变耗时，不能从两轮差值推断稳定改善幅度。

改后同一公开探针仍为 RED：首次 9,652 ms，后续三次 7,592/8,217/7,702 ms，后续 P95 8,217 ms。所有数据、当前版本、固定历史和全量重算断言通过，最后因 1 秒阈值失败。该结果没有证明稳定提速；本切片提供的是语义等价的固定准备接缝，不把代码中减少一次重复准备视作性能达标。

本次语义回归、优化后小样本与仍未通过的性能目标详见外部证据 `E:/GenCode/Skynet-evidence/v2-2026-10-04/54-profile-preparation-*`。当前仍重复的洞察、等待和多日期活动准备需要另行测量与优化；本切片不声称员工画像达到 AC32。
